# Incident: agent-1 lost DNS and its clock after a VPS resize (2026-10-10)

**Summary.** `agent-1` was resized on InterServer from 2 to 3 slices: 1 vCPU / 3.3 GiB became 2 vCPU / ~5.4 GiB. It
came back Ready, and everything that was already on it kept running. But its host could no longer resolve any
hostname, and its clock was 4 hours behind and couldn't sync. Nothing failed loudly. The only visible symptom was
three ArgoCD pods stuck in `ImagePullBackOff`.

**User impact: none.** The public site stayed up the whole time, because the portfolio pods were moved off the node
before the resize. ArgoCD kept working because a rollout keeps the old pods running until the new ones are ready.

---

## Fix runbook (copy-paste)

Use this when a node's host can't resolve names (`getent hosts quay.io` prints nothing) but `ping 1.1.1.1`
works, and `/etc/resolv.conf` says "generated by tailscale".

**1. Diagnose on the node over SSH.**
```bash
date; timedatectl                             # clock right? "System clock synchronized: yes"?
cat /etc/resolv.conf                          # "generated by tailscale" + nameserver 100.100.100.100 ?
resolvectl status | head -25                  # the real upstream DNS servers are listed under eth0
getent hosts quay.io                          # empty = host DNS is broken
ping -c2 1.1.1.1                              # works = the network is fine, only DNS is broken
tailscale status | tail -8                    # bottom "Health check" section shows Tailscale's own complaint
dig +short quay.io @<eth0 DNS server>         # works = upstream DNS is fine
dig +short quay.io @100.100.100.100           # empty = Tailscale's DNS forwarder is the broken piece
grep K3S_URL /etc/systemd/system/k3s-agent.service.env   # must be an IP, not a *.ts.net name (see step 2)
```
On a Mac, compare with `date -u`. Also look at event timestamps: `kubectl get events` with a
`firstTimestamp` hours away from the real time means that node's clock is off.

**2. Fix DNS.** Only do this if `K3S_URL` is an IP, because these steps turn off `*.ts.net` name resolution on the node.
```bash
tailscale set --accept-dns=false              # stop Tailscale owning DNS on this node (persists across reboots)
ln -sf /run/systemd/resolve/stub-resolv.conf /etc/resolv.conf   # Tailscale did NOT restore the file itself
getent hosts quay.io                          # should print addresses now
curl -sI https://quay.io/v2/ | head -1        # any HTTP status (401 is normal) = image pulls will work
```

**3. Fix the clock.** Ubuntu 26.04 uses **chrony**, not `systemd-timesyncd`.
```bash
systemctl restart chrony
sleep 10
chronyc makestep                              # jump now: after its first few updates chrony only slews,
                                              # and slewing 4h would take weeks
chronyc tracking | head -4                    # Reference ID = an NTP server, "System time" ~0 seconds
timedatectl | grep -E 'Universal|synchronized'   # "synchronized: yes" may take a minute or two
```

**4. Let Kubernetes catch up.** Pods in `ImagePullBackOff` retry on their own, after up to about 5 minutes.
To check from the Mac:
```bash
kubectl get pods -A -o wide | grep -v Running
```

**To undo step 2** (to use MagicDNS on the node again): `tailscale set --accept-dns=true`.

## Root cause (what is known, and what isn't)

**Known:**
- The host's `/etc/resolv.conf` was written by Tailscale (MagicDNS) and sent every lookup to its local forwarder,
  `100.100.100.100`.
- After the reboot that forwarder answered nothing. Tailscale's health check said
  `failed to fetch the DNS configuration of your device: exit status 1`.
- The provider's DNS servers, and public DNS like 1.1.1.1, worked fine when queried directly.

**Why nothing else noticed:**
- **Pods** resolve names through CoreDNS, not the host, so running workloads were unaffected.
- Only things the **host** does needed DNS: **image pulls** by containerd, and **NTP**.
- Images that were already cached on the node (portfolio, cert-manager) started fine, which hid the problem until an
  uncached image was needed.

**The clock:**
- The node came back about 4 hours behind. That's exactly the US Eastern offset, and the provider is in New Jersey.
  It looks like the VM was booted with its hardware clock set to local time. This is likely, but not confirmed.
- NTP would normally correct that within seconds. But chrony couldn't resolve its servers, since it uses NTS, and the
  server names go through the same broken DNS. So one fault caused the other.

**Not known:**
- Why Tailscale's DNS configuration failed after this particular reboot. "exit status 1" points at Tailscale failing
  to read the OS DNS settings it forwards to. A wrong clock at boot could plausibly contribute, but that wasn't tested.

## What would have caught it sooner

- An alert on pods in `ImagePullBackOff` or `ErrImagePull`. Alertmanager is disabled today.
- An alert on node clock skew. `node_timex_offset_seconds` and `node_timex_sync_status` come from node-exporter,
  which already runs on every node.
- After any node reboot, a check of `getent hosts quay.io` and `timedatectl` on the node before calling it done.

## Notes for a blog post

Working title: **"The resize that went fine, except it didn't: DNS, time, and a hidden dependency."**

Angles that make it worth reading:
- **Everything looked healthy.** Node Ready, apps Synced, site 200. The only sign was one pod type stuck on a pull,
  because cached images hid a host with no DNS. *Healthy dashboards can hide host-level failures.*
- **Two symptoms, one cause.** A 4-hour clock skew and failing image pulls looked unrelated. Time sync needs DNS, so
  broken DNS also froze the clock.
- **Pods and hosts resolve names differently.** Pods use CoreDNS, while containerd and chrony on the host use the
  host's resolver. That's why workloads were fine and image pulls weren't.
- **Small surprises from the OS:** Tailscale owning `/etc/resolv.conf` and not putting it back, and Ubuntu 26.04
  moving from timesyncd to chrony, where `makestep` matters for big jumps.
- **The planned part went well.** The drain kept the site up: a temporary label let the laptop node host the pods,
  and the PDB moved them one at a time. That's the contrast to the unplanned part.
